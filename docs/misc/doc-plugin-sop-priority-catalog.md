# Cross-repository security and conformance: priority catalog

Working catalog, 2026-09-09. Serves [tap#269](https://github.com/unified-systems-com/tap/issues/269).
Purpose: extract TAP's existing practices into an auditable plugin baseline. This is a prioritization proposal, not a new normative spec or a claim that every plugin already meets it.

The active roadmap step is [git-serious on our own repository](../../plan/road-products.md#step-products-git-serious-self): make our CI/CD legible. This catalog supplies the control vocabulary for that view; distributing controls and changing enforcement are subsequent work.

## Evidence and scope

Inspected TAP checkout `d5b8db5c10d7b5dc2c8290280269a30d5e096c9a`, its workflows, guards, validator, canonical specs, scanner configuration, and release tooling. Archived specs were excluded. Read the project board and existing issues. No application code, repository settings, plugin repositories, or grid data were changed; no security scan or test suite was run.

Live GitHub reads on 2026-09-09 confirmed TAP's effective `main` rules require `gate` (Actions integration 15368), `SonarCloud Code Analysis` (12526), and `Codacy Static Code Analysis` (56611). Layered PR rules include one required approval and code-owner review. CodeQL default setup is configured. These observations do not establish current bypass configuration, vendor quality thresholds, successful recent execution, or fleet-wide adoption.

The fleet counts in #269 were measured on 2026-09-01; they are historical evidence, not a fresh audit. Likewise, the Validation Map's older counts of plugin runtime coverage must not be shown as current. Some spec summary statuses lag their detailed requirements and implementation. Preserve the distinction between policy, implementation, configuration, and an observed successful run.

## Priority table

P0 = establish the minimum trustworthy baseline first. P1 = complete artifact and behavioral assurance next. P2 = sustained operations and deeper assurance. Priority is rollout order, not vulnerability severity. Conditional P1 controls become prerequisites before releasing or deploying the corresponding artifact.

## Reusable structure and visualization

Keep three layers distinct: **org policy** (rulesets, App grants, reporting defaults), **shared executable controls** (TAP workflows/parsers/guards), and **plugin-owned declarations** (identity, dependencies, test stack, domain specs, relevant exceptions). A plugin is a thin consumer of the shared implementation. Do not copy TAP's complete workflows, ratchet baselines, scanner exemptions, or container/FIPS build recipe into every plugin.

There is a decision to reconcile before implementation: #269 originally proposed a separate `tap-plugin-baseline` repo; the newer release-conventions section explicitly selects two homes and rejects a third standards repo. Follow the current spec for this catalog; reconcile the older issue's implementation plan when scoping the rollout.

For the first TAP visualization, use rows = repositories and columns = SOP controls, grouped by priority. Each cell should carry **applicability, expected policy, observed status, enforcement mode, evidence revision/digest, observation time, and owning issue**. Drill-down should connect the required check to its workflow or App producer and its concrete run. Existing Validation Map rows remain the authority for internal validation surfaces; the SOP view groups and references them rather than replacing that generated map.

Use separate statuses for pass, fail, missing, stale, unknown, and not applicable. An applicable advisory scanner with findings is not equivalent to an admission failure; an unavailable API is not evidence that a control is disabled. A green workflow running only structure checks must not paint runtime, spec, SBOM, and security columns green.

These fields are a design sketch, not a new stored format. If persisted, first use the existing graph vocabulary where its contracts fit; controls and observations needing identity/history deserve dedicated types. Any new file format requires a JSON Schema and load-time validation in the same change.

## Suggested execution order

1. Use this catalog under #269 to audit TAP itself against live controls and recent runs. Reconcile policy/implementation/observation differences before establishing a reference baseline.
2. Resolve the dependency-visibility (#268), runtime-depth (#187), and spec-discipline (#286) contracts; pilot the shared checks on one dependency-bearing plugin with specs and runtime tests.
3. Observe negative controls as well as successful runs. Build the repo-by-control visualization from those observations.
4. Distribute the established baseline through reviewable plugin PRs. Update creation scaffolding under [#203](https://github.com/unified-systems-com/tap/issues/203), then add recurring drift checks. Scan release inventories under #264 rather than treating SBOM production as completion.

No new dependencies, external writes, automatic distribution, or enforcement changes are part of this cataloging pass.
