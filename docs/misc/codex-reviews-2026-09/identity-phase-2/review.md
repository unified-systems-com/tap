**Recommendation: preserve the identity direction; revise the execution contract before starting the implementation sequence.** The plan is materially better than the pre-audit version, but “eight independently landable pieces” is not yet true. Its largest risks are in interactions between otherwise reasonable decisions: immutable keys versus replacement, durable failures versus batch idempotency, reference resolution versus existing preflight invariants, and advisory locks versus every other writer.

## Findings that should change the plan

### 1. The immutable-property rule is internally inconsistent, and replace is the main import path

The proposal allows a missing constituting value to arrive later and the key to move `null → value`. It simultaneously refuses any patch containing a `NATURAL_KEY` property. That makes the advertised first-assignment path unavailable through patch. It also rejects harmless assertions of the same value. Most seriously, the rule says nothing precise about **replace**, which GRIFT actually uses for existing nodes: [tap_grid/grift/importer.py:2350](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2350). Replace sets supplied fields and resets omitted optional fields to defaults: [tap_grid/services/_impl.py:119](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/services/_impl.py#L119).

There are two bad straightforward implementations:

- Guard only patch: an id-addressed replace changes a constituting field while the write-once spine key retains its old value. The next ref import resolves using stale identity.
- Extend the set-intersection ban to replace: ordinary re-import of a Page or Panel fails, because their required payload includes `slug`, which is also their key. See [tap_web/models.py:33](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L33), [tap_web/models.py:44](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L44), [tap_web/models.py:135](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L135), [tap_web/models.py:147](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L147).

**Change the mechanism, preserve immutability.** Compare the persisted constituting values with the effective post-write values. Equal values are legal; changing an established value is refused; first assignment of an absent value needs a deliberately specified rule. Composite keys need this at the member level: having a null *whole key* does not license changing an already-known member while filling a different missing member. Protect against replace omission/defaulting too. Non-key patches still require no hash. Compute a key only for creation or a sanctioned completion of an incomplete document.

SCIM supplies unusually exact prior art: replacement may repeat immutable values, and initially absent immutable attributes may acquire a value. The proposed set intersection confuses field presence with mutation. [RFC 7644 §§3.5.1–3.5.2](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.5.1).

A malformed observation can still need correction. Preserve the chosen refusal of ordinary re-keying, but name the current operator route: correct the owning declaration/data through the approved migration or explicit retirement/new-lifetime procedure. “A changed value is a new thing” is a domain choice, not a proof that erroneous observations cannot occur. It is especially unsuitable as the only explanation for web route edits.

### 2. The existing keyed core types do not both fit the promised lifetime semantics

Page’s `slug` is globally unique in its typed table: [tap_web/models.py:65](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L65). A tombstoned Page still occupies that value. Ignoring it during live resolution and assigning a new UUID cannot make the new Page insert legal. The plan’s most important lifetime example needs a test against actual typed constraints, not just Entity rows.

Panel has the opposite problem: its slug is explicitly **not globally unique**, and its URL contains the entity UUID as well. Nevertheless `NATURAL_KEY = ("slug",)` declares slug sufficient for correlation. Two legitimately different panel instances may therefore be an expected ambiguity rather than evidence of a broken collector. See [tap_web/models.py:129](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L129) and [tap_web/models.py:149](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L149).

Settle whether these authored types should participate in observational resolution at all, and at what granularity. Do not casually remove Page routing guarantees or add uniqueness to natural keys. This is a model-semantics question before it is a migration task. Filed as [tap#555](https://github.com/unified-systems-com/tap/issues/555), parented to #140.

### 3. Durable failed Batches change idempotency and retry semantics

Today the Batch is created **inside** the same atomic block as its members; rollback removes it. The failure handler does not call `fail_batch` on a durable row. See [tap_grid/grift/importer.py:2266](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2266), [tap_grid/grift/importer.py:2289](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2289), [tap_grid/grift/importer.py:2723](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2723). `write_batch` likewise ensures its Batch inside the transaction: [tap_grid/services/__init__.py:244](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/services/__init__.py#L244).

Adding `failure` is reasonable, but not sufficient. Once a failed Batch persists, the current presence-only import check treats it as already imported and skips a retry: [tap_grid/grift/importer.py:1657](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L1657). Force-reimport is DEBUG-only: [tap_grid/grift/importer.py:3261](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L3261). A retry can therefore turn “nothing applied” into an apparently harmless skip unless the state machine changes or the contract requires a fresh attempt ID and surfaces the prior failure explicitly.

Specify the persistence boundary: roll back graph-member changes, then persist the failure record in an authorized transaction; emit the Flaw after that record is durable. Define failure-record persistence failure, concurrent attempts of one batch ID, failed-ID replay, successful retry, and force-reimport of an existing successful batch that now fails. Do not overwrite a historical successful attempt’s truth accidentally. Dry-run/validation must have an explicit side-effect rule.

The proposed singular shape `{kind, entity_type, natural_key, ref, candidates}` also cannot satisfy its own two-ambiguity done-test. Use a bounded list of issue objects with a total count and truncation indicator if needed. Edge duplicate-input failures need input paths/refs and endpoint IDs, even when no stored candidate entity exists; do not invent candidate UUIDs just to fit a node-only schema. The current pipeline stops at the first failed operation, so collecting all ambiguities requires a planned resolution/validation pass, not just a different exception: [tap_grid/services/__init__.py:252](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/services/__init__.py#L252).

Keep the failure field on Batch rather than hiding lifecycle state in user-supplied `metadata` ([tap_grid/models.py:1201](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/models.py#L1201), [tap_grid/models.py:1245](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/models.py#L1245)). Validate its declared schema on the write path and make it lifecycle-owned. The Batch already represents the failed occurrence; a new failure node is unnecessary for this slice.

### 4. XOR is sound, but the ref protocol is substantially underspecified

Retain `entity_id XOR ref` on a member envelope. It avoids two competing addressing authorities. It does **not** define endpoint addressing, Batch identity, or identity collisions after resolution.

Concrete omissions to settle before schema work lands:

| Surface | Required decision |
|---|---|
| Batch envelope | It reuses `GriftEntityEnvelope`, but Batch is KEYLESS. Does it remain id-bearing? If yes, change the objective from “no entity_id at all” to “no member entity IDs.” A shared-schema relaxation must not accidentally admit unresolvable ref-only Batches. |
| Endpoint syntax | Declare `from_entity_id XOR from_ref` and the analogous target shape, or an equally unambiguous tagged reference. Specify empty refs, duplicate refs, cross-batch refs, UUID-shaped refs, and references to edges. |
| Existing endpoints | An edge may need to point to an already stored node without re-observing/replacing that node. Preserve explicit endpoint IDs for that case. github_core’s enrichment already emits edges with `nodes=[]`. |
| Missing node key | A keyed type with incomplete values produces null. It cannot participate in lookup. Ref mode should refuse it by a dedicated, property-naming error; never look up `natural_key IS NULL`, and never silently mint a new occurrence every replay. |
| Same key under two refs | Decide whether this is rejected or unified, and how conflicting payloads are handled. Do not leave order-dependent last-writer-wins as an accidental consequence of the ref map. |
| Mixed ID/ref aliases | An id envelope and a ref envelope can select the same row. Different refs can select the same row. Run duplicate-write and upsert/removal checks on **resolved IDs**, not only source strings. |
| Payload references | Endpoint remapping is not arbitrary UUID substitution. Model-owned UUID fields and hotlink payloads need either a declared transport form or an explicit unsupported boundary. |
| Result | Return enough `ref → assigned ID`, outcome, and version information to let callers make subsequent explicit operations. Scope the map to its Batch. |

Evidence: shared envelope [tap_grid/schemas/grift-document.schema.json:32](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/schemas/grift-document.schema.json#L32) and [tap_grid/schemas/grift-document.schema.json:134](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/schemas/grift-document.schema.json#L134); endpoint schema [tap_grid/schemas/grift-document.schema.json:94](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/schemas/grift-document.schema.json#L94); null-key semantics [tap_grid/natural_key.py:146](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/natural_key.py#L146); enrichment [tap_plugin/github_core/collectors/github_collector/collector.py:1252](https://github.com/unified-systems-com/tap-plugin-github-core/blob/4f1cb7fbbc7f2dfdeb5da7a19b07fc8d3cf7c211/tap_plugin/github_core/collectors/github_collector/collector.py#L1252); payload hotlinks [tap_web/models.py:46](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_web/models.py#L46).

There is also a phase-3 design debt to name now: ref mode rejects KEYLESS types, but some collector-created things are occurrences with no repeatable source identity. They still need a legal mint path. The slogan “a collector never supplies an ID” and the two supported envelope modes do not by themselves provide it. Preserve the explicit-ID migration path until this is decided; do not pretend all collector output is correlatable.

### 5. Resolution must re-run identity checks that preflight currently performs on literal IDs

Existing preflight rejects an entity used for both upsert and removal anywhere in the document: [tap_grid/grift/importer.py:1846](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L1846), governed by [tap_grid/specs/spec-grid-import-grift.md:321](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/specs/spec-grid-import-grift.md#L321). A ref can resolve to that removal target without sharing any input ID. A preflight-only literal set intersection no longer enforces the contract.

Forced sweep also derives “present in revised content” directly from each envelope’s `entity_id` and the literal endpoint IDs: [tap_grid/grift/importer.py:2887](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2887). Passing the original ref-bearing document to it would crash or produce the wrong presence set. It needs resolved membership, including objects reused rather than created, within the same transaction. “Nothing retires” is misleading if ref batches may use existing force/sweep machinery; either support it with tests or reject that combination explicitly.

Cross-batch resolution adds another choice: current literal duplicate detection is document-wide, while refs are batch-local and each batch commits separately. If two batches resolve to one identity, is that sequential observation or forbidden duplicate input? Define it; do not discover the rule after earlier batches commit.

### 6. The advisory-lock ruling is viable, but “one line of SQL” is not its proof

A transaction-scoped lock can serialize two **cooperating resolutions** of one absent key. Keep that ruling. Complete the protocol:

1. Derive from validated, normalized model values; acquire a stable namespaced lock before lookup; re-read after acquiring it; hold it through typed row, spine, edges, and transaction commit.
2. Define deterministic acquisition order for batches needing A and B. Opposite input order otherwise creates an advisory-lock deadlock. Include row locks taken by OCC/removals in the order analysis.
3. Define a separate edge lock identity based on semantic edge type plus resolved endpoint lifetimes. Edge is KEYLESS today ([tap_grid/models.py:904](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/models.py#L904)); a node `(entity_type, natural_key)` lock does not describe per-pair edge exclusion.
4. State that explicit-ID creates still may deliberately produce a second live row with a key. A resolver-only advisory lock cannot stop an authored writer that does not acquire it. Even if all writers participate, a lock does not turn an explicit create into a resolution. Promise resolver race safety, not global uniqueness.
5. Handle a delete/purge between selection and mutation. Existing OCC takes a row lock only when a version expectation is present ([tap_grid/services/_impl.py:353](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/services/_impl.py#L353)). Verify liveness under the mutation lock, or fail/re-resolve according to an explicit rule; never return a successful new observation of a tombstone.
6. Bound lock wait and account for the number of locks held until a large batch ends. Do not turn memory/timeout/deadlock failures into identity ambiguity.

The importer presently builds create/replace operations before executing them ([tap_grid/grift/importer.py:2302](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2302)). If the new resolver merely reserves a UUID without inserting the row, a second same-key member in the **same transaction** can still see zero persisted rows; advisory locks are reentrant for their owner. If it instead creates each row immediately, it must preserve deferred hotlinks, authorization, provenance, rollback, and one version bump. The proposed signature `resolve_identity(entity_type, key_document | natural_key)` does not explain where the required non-key fields come from. Make the public service accept the declared properties plus creation payload/context, or specify the private planning/result boundary. A caller-supplied precomputed natural key must not become a new authority to create or select rows.

`hashtext` is a small hash for a lock key, not an identity hash. Collisions cause unnecessary serialization, not incorrect selection if the subsequent lookup uses the full key. Prefer a documented stable 64-bit mapping with a lock-domain prefix; do not use Python’s process-randomized `hash()`. Sorting must be consistent in the actual lock identity space. PostgreSQL-specific coupling is an acknowledged tradeoff against TAP’s SQLite direction, not a reason to build a portability framework now.

These are application-protocol requirements: PostgreSQL documents voluntary advisory locks, automatic transaction release, deadlock behavior, and finite lock memory. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS). READ COMMITTED permits the post-wait query to see a newly committed row; a stronger fixed snapshot needs a different retry/failure story. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html).

OCC is a separate contract. On explicit IDs, retain current expected-version checks. On refs, a version number alone does not identify an observation lifetime: old A/version 1 can be retired and new B/version 1 can occupy the key. Either refuse `entity_expected_version` in ref mode for this slice, or bind the expectation to the previously observed entity identity as well. No match with an expectation must never silently become create. Existing behavior is at [tap_grid/grift/importer.py:2324](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/grift/importer.py#L2324).

### 8. The supposedly settled derivation has an actual discriminator bug and a false proof

`key_document()` writes `{"type": entity_type}`, then copies each supplied property into that same dictionary. A property named `type` overwrites the discriminator: [tap_grid/natural_key.py:152](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/natural_key.py#L152). I executed the exact pinned module under Python 3.14.7:

```text
natural_key("one__thing", {"type": "same", "id": "7"})
== natural_key("two__thing", {"type": "same", "id": "7"})
# True
```

The resolver’s separate entity-type predicate limits the consequence, but the cross-type correlation guarantee itself is false. Reserve/reject this property name, or deliberately change the document structure with migration accounting. Current declared core keys do not use it; this is an accepted-domain bug to fix before plugin recipes spread it.

The “provably equivalent to JCS” claim also fails for the allowed integer domain. Python emits `9007199254740993` exactly and `10**21` as full decimal. ECMAScript number serialization does not behave that way. The validator accepts arbitrary integers ([tap_grid/natural_key.py:113](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/natural_key.py#L113)), while the proof assumes that excluding floats excludes numeric differences ([tap_grid/natural_key.py:88](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/natural_key.py#L88), [tap_grid/specs/spec-grid-entity.md:897](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/specs/spec-grid-entity.md#L897)). Keep the chosen TAP canonicalizer; remove the false proof or explicitly constrain the numeric domain. Do not change key bytes incidentally. [RFC 8785 number serialization](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.2.2.3). Filed together as [tap#554](https://github.com/unified-systems-com/tap/issues/554).

Declaration validation should also reject empty/invalid member tuples and unknown fields rather than turning a misspelled property into a missing observation. Today backfill uses `getattr(..., None)` ([tap_grid/management/commands/backfill_natural_keys.py:89](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/management/commands/backfill_natural_keys.py#L89)), while field-existence enforcement is a **core-only test**, not a plugin runtime declaration gate ([tap_grid/tests/test_natural_key.py:186](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/tests/test_natural_key.py#L186), [tap_grid/tests/test_natural_key.py:230](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/tests/test_natural_key.py#L230)). A protocol that accepts partial observations needs a separate way to distinguish an invalid recipe from valid missing data.

### 9. One Flaw per failed batch is sensible aggregation; unconditional AppFlaw is not justified

The Batch should carry durable diagnostic detail; the Flaw can route an actionable invariant breach. But the existing spec assigns `app` to plugin contract violations, `code` to core violations, and `instance` to inconsistent runtime state. It excludes ordinary malformed input and anticipated errors: [specs/spec-tap-flaw-v0.md:69](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/specs/spec-tap-flaw-v0.md#L69), [specs/spec-tap-flaw-v0.md:99](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/specs/spec-tap-flaw-v0.md#L99).

Two candidates do not prove which actor caused them. An operator-authored duplicate, a core bug, a deliberately nonunique authored state, a bad recipe, and two repeated input edges are different causes. Preserve fail-closed and one aggregate signal; either explicitly narrow the AppFlaw ruling to a known plugin breach or amend the Flaw contract if this is intended to be a new convention. Do not invent a deferred `grid` class or policy framework. At minimum include the violated invariant and evidence, and avoid claiming “collector bug” from match count alone.

Also update caller integration: `CollectorBase.submit_grift` records produced Batches only from imported/skipped lists, then raises on errors ([tap_cares/collectors/base.py:300](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_cares/collectors/base.py#L300)). A newly durable failed Batch needs a discoverable link from the job/result without being mislabeled imported or skipped.

### 10. The landing sequence publishes unsupported contracts midway

## Authored IDs: explicit behavior table

“Skip resolution, stamp the key anyway” is sound **on create** and preserves authored authority. It does not mean ignore consistency with a row already at that ID.

| Input state | Required behavior |
|---|---|
| Supplied ID absent, complete valid key | Create at that assigned ID; stamp the derived key. A different live row with the same key does not authorize redirecting this write. The accepted nonunique storage contract must say whether this deliberate ambiguity is allowed. |
| Supplied ID exists, same type and same constituting values | Update non-key data under normal replacement/OCC rules; preserve its key. |
| Supplied ID exists, different established constituting value | Refuse a typed identity/property conflict atomically. Do not silently re-key, keep stale key, or redirect to the row matching the payload key. |
| Supplied ID exists with incomplete/null key | Compare existing members, permit only the declared first-completion case, and derive under the same atomic mutation. |
| Supplied ID is a tombstone | Retain terminal refusal. Ref resolution may mint another lifetime; explicit addressing must not resurrect the old ID. |
| Supplied ID exists with another entity type | Retain type-conflict refusal. |

This is why retaining the explicit `entity_id` argument is correct. It is also why “every id-bearing batch behaves byte-identically” is too broad: ordinary authored replay should remain compatible, but an id-bearing **key-changing** replacement becomes illegal under the new invariant. Revise that done-test explicitly.

## Prior art: where mature systems landed, and what transfers

The relevant evidence is not that many products say “identity.” It is how they specify the cases this plan leaves open. These are primary-source comparisons; none is a recommendation to adopt a new dependency or deferred subsystem.

| System | Established contract | Implication for TAP |
|---|---|---|
| **FHIR R5** | Conditional update distinguishes zero/one/multiple matches, rejects supplied-ID disagreement, and reports multiple matches as a precondition failure. Transactions support local fullUrl references and resolve links; identity conflicts fail the transaction. These conditional interactions remain designated trial-use in R5. | Closest transport/resolution analogue. Borrow the explicit case matrix and reference rewrite scope. A multiple match is a defined unsuccessful result, not automatically proof of an application bug. [HTTP contract](https://hl7.org/fhir/R5/http.html#cond-update), [transactions](https://hl7.org/fhir/R5/http.html#transaction). |
| **SCIM** | Provider-assigned stable IDs are separate from client external IDs, whose uniqueness is not server-enforced. Immutable values may be repeated on PUT and initially absent values may be assigned; bulkId links operations within a bulk request. Bulk processing is not the same all-or-nothing transaction model as TAP. | Strong support for the split and concrete correction to immutability. Do not copy externalId’s client authority into TAP’s server-derived key, or SCIM’s partial-failure semantics into GRIFT. [Schema](https://www.rfc-editor.org/rfc/rfc7643.html#section-3.1), [update/bulk protocol](https://www.rfc-editor.org/rfc/rfc7644.html). |

[Resource IDs](https://jsonapi.org/format/#document-resource-objects), [atomic operations](https://jsonapi.org/ext/atomic/). |
| **Kubernetes** | Names can be reused after deletion; UIDs distinguish historical object incarnations. Resource versions protect updates to a particular object. | **TigerGraph** | Declared edge discriminators are required on insert and immutable afterward; they permit multiple edges for a pair. | Supports EDGE_KEY’s semantics and the dependency before migrating existing meaningful parallel edges. | **Microsoft Dataverse** | Upsert explicitly selects by ID or alternate key. The strongest convergence is **assigned row/lifetime ID + explicit source identity + scoped local references + documented conflict outcomes**. The biggest divergence is TAP’s deliberately nonunique correlation key: it is legitimate, but it means candidate ambiguity and participating-writer serialization must be first-class contracts. None of these precedents makes the current eight-item sequence complete by analogy.

## The `0x6710` namespace/prefix proposal

**Recommendation: retain the current bytes for phase 2.** This is an optional human-recognition feature, unrelated to fixing resolution. A UI label or formatted presentation provides the same benefit without spending digest bits or changing every key.

Technically the prefix is allowed by UUIDv8: RFC 9562 reserves only the variant/version layout and leaves the rest implementation-defined. It explicitly does not promise uniqueness for arbitrary v8 layouts. [RFC 9562 §5.8](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.8).

Replacing 16 of 122 digest bits leaves 106. Birthday-scale work for an arbitrary collision drops from roughly `2^61` to `2^53`—256 times less work. For n independently distributed keys, the small-probability approximation is `n(n-1)/2^(b+1)`; the same population’s accidental collision probability rises by 65,536. At one billion keys that is approximately `9.4e-20` versus `6.2e-15`. Those probabilities are small, but a digest match selects an identity, so this is not just a cosmetic checksum. A fixed visual marker supplies no authenticity. This is also distinct from target preimage resistance.

The namespace UUID is a hash input, not an output prefix. Changing that constant alone will not produce `6710…` outputs; the layout must change. Existing canon fixes the slicing ([tap_grid/natural_key.py:47](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/natural_key.py#L47), [tap_grid/specs/spec-grid-entity.md:893](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/specs/spec-grid-entity.md#L893)) and an independent reconstruction test fixes its recipe ([tap_grid/tests/test_natural_key.py:45](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/tests/test_natural_key.py#L45)). If approved separately, change the declared byte layout, test vectors, migration/backfill accounting, and reference implementations together. The unchanged-lower-bits scheme leaves a tiny subset of old values already bearing the prefix unchanged; the key-space contract still changes globally.

The date claim is essentially correct: interpreting `0x6710 << 32` as the first 48-bit UUIDv7 timestamp gives **5560-12-01 18:05:37.664 UTC**. The version nibble already distinguishes v7 from v8, however, and neither marker proves derivation or ownership.

**Stored-key status is unverified.** A historical comment saying no keys had been stored when v8 was introduced ([tap_grid/natural_key.py:177](https://github.com/unified-systems-com/tap/blob/a6581ada042a61da8f3dbb3791b34066991d6c14/tap_grid/natural_key.py#L177)) is not a census today. Backfill can persist keys; exports and Gryphon can already read the field. I did not query every running grid or inspect offline customer databases. Do not authorize a no-migration layout change from “nothing reads them.” Before changing bytes, inventory non-null keys through each grid’s canonical read interface, plus exported artifacts, and establish the recomputation procedure including tombstones where retained correlation matters.

## Minimum acceptance matrix before calling phase 2 complete

1. Creation through generated-ID and authored-ID paths produces the same declared key for equal effective properties; callers cannot inject it. A failed typed validation leaves no orphan spine.
2. Repeated equal key values succeed; changed established values fail on patch and replace; omitted replace members cannot clear identity; incomplete composite keys can only follow the chosen completion rule.
3. Zero/one/multiple live matches behave as specified; tombstones never win; a supported typed object reappears under a new ID; previous endpoints still address the previous lifetime.
4. Same Batch replay tests **skip**; two distinct Batch IDs with the same observations test **resolution/upsert**. Do not pass the latter by accidentally exercising the former.
5. Duplicate refs, two refs/one row, mixed ID/ref aliases, undefined/cross-batch/edge refs, missing keys, and upsert/removal aliasing have explicit outcomes before any invalid batch commits.
6. Edge re-observation is stable; duplicate input and duplicate stored candidates fail atomically with useful detail; a mixed batch does not switch id-bearing edge semantics merely because it contains a ref node.
7. Concurrent absent-key resolutions with separate database connections create one identity; reverse-order two-key batches terminate under the chosen lock policy; concurrent edge resolution and delete/OCC races fail safely or commit a valid result. A later batch failure rolls back any earlier mint.
8. Two ambiguities survive as one failed Batch with both details, exactly the specified aggregate Flaw, and a discoverable job link. Retry, force-retry, concurrent replay, dry-run, and failure-record-write failure are exercised.
9. Backfill coverage, stored-key drift including null, and dimension-independent resolution readiness are separate truthful results. Legacy undeclared plugin types keep the explicitly supported ID-bearing path during migration.
10. Specs, schema, importer, error-code severity classification, discovery documentation, and skills agree at every intermediate landing. Canonical derivation vectors include reserved property names and numeric boundaries. Boot/read-grant checks verify Gryphon visibility after schema changes.
