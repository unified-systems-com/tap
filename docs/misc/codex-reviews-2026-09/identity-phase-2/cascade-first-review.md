## 1. The premise is right for TAP, but the absolute theorem is too broad

The actual contradiction is between **an identifier computed solely from unchanged source facts**, **permanent refusal to reuse a tombstoned row**, and **accepting a returning observation as a new lifetime**. Those three cannot all hold. The permission-gap example is sufficient; the source need not delete or reuse its own identifier.

There are logical alternatives: include a lifetime/generation discriminator in the derivation, retain one permanent source-object identity with separate observation lifetimes, or avoid retiring on this particular evidence. None is a free third way: the first needs durable generation coordination, the second changes the data model, and the third does not solve returns after a legitimate retirement. They do not overturn the chosen assigned-UUIDv7 direction. Similarly, a pure function could include a perspective argument; the stronger accurate statement is that the **same source-facts-only function** cannot name two perspective-local rows. No perspective work is needed now.

**The importer currently refuses the whole affected batch; it does not revive the node.** On pinned main, `Entity.objects` sees tombstones, so the importer routes an existing ID to `replace_node` [tap_grid/grift/importer.py:2322](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2322) [tap_grid/grift/importer.py:2350](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2350). The service loads the typed row through `all_objects` and returns `entity_tombstoned` for a non-delete mutation [tap_grid/services/_impl.py:390](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/services/_impl.py#L390). `write_batch` raises its rollback sentinel on a failed result [tap_grid/services/__init__.py:244](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/services/__init__.py#L244), and the importer propagates operation failures into its own batch rollback [tap_grid/grift/importer.py:2531](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2531) [tap_grid/grift/importer.py:2723](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2723). This is a source trace, not a newly executed importer test. A replay of an already-recorded batch can instead be skipped before its members execute [tap_grid/grift/importer.py:1657](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L1657); the regression fixture must use a fresh batch ID. Batch atomicity also does not imply that every other batch in a multi-batch document rolls back.

**Move the one-fixture tombstone test forward in the verification list.** It is cheap proof of the premise, not a demand to implement resolution. Include a live sibling write in that same failing batch and prove it rolls back too.

The “only needed at authority ON” explanation is false as a claim about existing surfaces: ordinary `delete_node` exists now [tap_grid/services/__init__.py:410](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/services/__init__.py#L410), imperative GRIFT removals already build delete operations [tap_grid/grift/importer.py:2514](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2514), and force-reimport can sweep missing members [tap_grid/grift/importer.py:2695](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2695). The gate can still wait, but until it lands a derived-ID collector cannot refill such a tombstone. Describe an unsupported workflow, not an impossible state.

The AD analogy also needs correction. ## 2. Challenge each withdrawal without restoring the withdrawn scope

### Hash withdrawal: agree with the decision, replace the historical justification

Strongest objection: a fixed-size derived digest can offer a common indexed representation across heterogeneous types; deleting it loses a possible optimization. That does **not** change the ruling. The immediate operation is equality search over known typed columns, so direct indexed fields are sufficient and avoid a second representation with its own canonicalization rules.

“No established system does this” is not a defensible universal conclusion from the named sample. Data Vault explicitly distinguishes **primary-key hashing** from satellite hashdiffs; saying its hashdiff is change detection does not exhaust its use of hashing. That is not an exact precedent for TAP's deliberately nonunique secondary digest, but it defeats the shortcut argument that Data Vault uses hashes only for change detection. DataHub URNs are its resource identity, not simply a secondary key behind TAP-like assigned lifetime IDs. Atlas is the better two-key comparison. [AutomateDV hashing](https://automate-dv.readthedocs.io/en/latest/best_practises/hashing/), [DataHub concepts](https://github.com/datahub-project/datahub/blob/master/docs/what-is-datahub/datahub-concepts.md), [Atlas type system](https://atlas.apache.org/0.8.3/TypeSystem.html).

Use the sufficient rationale: **“Typed-field search satisfies the current need; a stored digest has no required consumer.”** Do not restore the hash.

### Resolution withdrawal from phase 2: agree, with a workflow fence

Strongest objection: building retirement before return-capable ingestion can strand returning source objects. That changes the rollout boundary, not the implementation scope. Keep retirement manual and explicit; do not claim a supported retire/recollect loop until the gate. Phase 3 must not remove existing producer recipes before there is a working replacement transport and resolver.

### Generalized cascade withdrawal: agree, but atomicity has conditions

Strongest objection: preflight can report all blocked children before mutation and provides a stable closure for review. Those are useful future affordances. They are not required for fail-safe **database state** if every mutation shares the transaction and every unsuccessful child aborts the outer operation. The current `write_batch` result-to-rollback conversion provides that boundary [tap_grid/services/__init__.py:252](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/services/__init__.py#L252). Merely returning a failed child result without escalating it would not.

Rollback does not reverse emitted network calls, logs, in-memory state or all signal side effects. Keep the walk database-local and defer any external success notification until commit. Nor does `atomic()` alone promise a stable closure against concurrently inserted/reparented edges. The make-it-work scope can defer a comprehensive concurrency protocol, but must not claim a serializable snapshot of a changing subtree. Django explicitly separates database rollback and commit callbacks. [Django transactions](https://docs.djangoproject.com/en/5.2/topics/db/transactions/).

## 3. The small cascade is the right mechanism; its guarantees need tightening

Follow the latter. The strongest objection is duplicate enumeration and the possibility of drift. The subset-of-permission guard addresses the immediate inconsistency [tap_grid/models.py:746](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/models.py#L746). A model-local declaration also preserves source-type context that a globally named edge type can lack. No edge-registry redesign is needed now.

But **“one declaration, three readers” is an intended convergence, not the present implementation**. The design record still describes a separate manifest descent table [docs/misc/doc-grid-reconcile-design.md:91](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/docs/misc/doc-grid-reconcile-design.md#L91), later calls that manifest the cascade table [docs/misc/doc-grid-reconcile-design.md:591](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/docs/misc/doc-grid-reconcile-design.md#L591), and even retains the old `OUTBOUND_EDGES` bit at line 600. Do not require the whole collection plan to fit a tuple of edge names.

### The cap can silently permit a partial cascade — fix now

At PR head, `_contained_children` applies `DISTINCT … LIMIT` before excluding the node currently being retired [tap_grid/services/_impl.py:199](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/services/_impl.py#L199). That node is already in `visited` but is still live during child discovery [tap_grid/services/_impl.py:610](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/services/_impl.py#L610). The queue later skips it [tap_grid/services/_impl.py:653](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/services/_impl.py#L653).

Counterexample: cap 2; live nodes R, A, B; edges R→R, R→A, R→B. A legal result order returns R,A under `LIMIT 2`. The walk retires R, skips its self-reference, retires A, and reports success; B survives after its containing edge has ended. The actual closure has three nodes and should cause atomic refusal. No query ordering guarantee excludes this case.

I executed the exact pinned deletion branch and helper with ORM doubles under Python 3.14. The result was `success=True`, R/A retired, B live. This verifies the control-flow defect; a service-boundary database regression remains the done-test. Fix bounded enumeration so the overflow witness survives exclusion/deduplication. Preserve bounded reads and cycle termination. Filed [tap#572](https://github.com/unified-systems-com/tap/issues/572), parented to #140.

### Two parents: not universally wrong, but “collection reached it” is not ownership

The chosen rule is defensible for a component whose validity requires both parents; losing either parent ends it. It is wrong for a shared source object that remains valid through another owner. A shared account reached from two repositories must not be retired because one repository disappears. Kubernetes deliberately preserves a dependent while a valid owner remains; Datomic components represent things that exist as parts of a parent. These are different lifecycle models, not implementations of one universal rule. [Kubernetes garbage collection](https://kubernetes.io/docs/concepts/architecture/garbage-collection/), [Datomic components](https://docs.datomic.com/schema/schema-reference.html#db-iscomponent).

Do not build an ownership policy engine now. Keep shared things off containment, and review the first real plugin declarations against concrete examples. The small walk can remain cycle-safe even if malformed ownership cycles are tolerated temporarily. Also amend the promise that two-parent retirement “logs both parents”: the supplied walker reads outgoing child lists and tracks visited IDs; it does not inspect and warn about two incoming owners [tap_grid/services/_impl.py:199](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/services/_impl.py#L199) [tap_grid/services/_impl.py:646](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/services/_impl.py#L646), despite the spec wording [tap_grid/specs/spec-grid-service-delete.md:406](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/specs/spec-grid-service-delete.md#L406). The warning can be deferred honestly along with integrity findings.

## 4. Generated search and the placeholder are acceptable small steps

**`find_existing`: yes.** Direct equality filters on declared typed fields, live-only scope and loud ambiguity are a sensible primitive. It must stay a search: it has no authority to mint, lock or guarantee uniqueness. The supplied implementation rejects undeclared types separately from KEYLESS, requires exactly the declared argument names, returns none for explicit `None`/empty values, and caps ambiguity candidates [tap_grid/models.py:789](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/models.py#L789). Thus SQL `NULL` is not used to match all incomplete rows. An omitted kwarg is an API error, whereas an explicitly absent value returns none; document that distinction.

**At the gate, missing identity is not automatically permission to mint on every poll.** A complete key with zero matches and an incomplete key are different inputs even if this helper returns `None` for both. Let the importer check completeness before calling it. Occurrence/KEYLESS writes need a separate supported mint path; defer that transport decision to the gate.

**Indexes: yes, reuse existing coverage.** Page's unique slug already supplies its access path; Panel needs the new slug index. The implementation does that instead of blindly adding two redundant indexes [tap_grid/models.py:545](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/models.py#L545). Verify the actual migration/DB index, not just an `_meta` declaration. A plain composite index is enough now; partial indexes, broad query-plan tuning and plugin-wide performance work can wait. Index generation at `ready()` changes model metadata; migrations still create the physical index.

**KEYLESS wording:** the implementation inherits the classmethod and raises `TypeError`, rather than making the method absent. That is a reasonable simpler API. Say “cannot be searched,” not “has no method.” Core-only declaration coverage is sufficient for this core-only phase, not for phase 3's claim about every plugin. Generate conformance checks per installed plugin as it migrates; do not break all currently undeclared plugins now.

**Placeholder: harmless if it makes no claims.** The strongest objection is that a column without a consumer adds schema/API baggage and invites accidental use. It does not justify spending this pass removing and later restoring the surface. Suggested wording: “Reserved nullable text. Always null in this phase. Not an identifier, lookup key, populated projection or uniqueness guarantee. External input is refused. A later spec and migration must define its first writer and consumer.”

The supplied PR #564 includes both the type alteration and a subsequent clearing migration, so old hashes are not simply cast to plausible-looking text [tap_grid/migrations/0004_entity_natural_key_placeholder.py:1](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/migrations/0004_entity_natural_key_placeholder.py#L1) [tap_grid/migrations/0005_entity_natural_key_clear.py:1](https://github.com/unified-systems-com/tap/blob/064678a59950ef43e32bc3dbc11d0b95571ed20b/tap_grid/migrations/0005_entity_natural_key_clear.py#L1). This is better than assuming no grid ever ran the backfill. Describing a possible future composed identifier is fine; pre-committing its uniqueness semantics is unnecessary. The no-reader claim also needs the obvious exception for existing export/Gryphon serialization of the reserved null field.

## 5. At the gate, prefer A; B is not a semantics-free compatibility shortcut

**Strongest case for B:** unchanged collectors continue emitting existing payloads; the importer absorbs lifetime turnover. That could lower immediate producer churn. It loses the argument under the settled rules:

1. **Caller authority returns.** A collector-chosen UUIDv5 becomes the stored correlation handle. That contradicts the declaration-derived, never-supplied identity rule and preserves the old producer recipe dependency under a new column name [tap_grid/specs/spec-grid-entity.md:874](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/specs/spec-grid-entity.md#L874) [tap_grid/specs/spec-grid-entity.md:879](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/specs/spec-grid-entity.md#L879).
2. **Zero-match behavior is missing.** If the importer creates at the incoming derived ID, AC-1 remains false. If it assigns a UUIDv7 immediately, mapping is needed from the first import, not just on return from a tombstone. “No plugin change” does not mean no protocol change.
3. **Two collectors do not converge merely by using handles.** If they have different recipes/namespaces for one source object, one text value does not relate them. If they already use exactly the same recipe, B inherits that fragile agreement; it has not replaced it with the model declaration. Adding a facts lookup to solve this would bring back A's resolver work.
4. **The column would have incompatible meanings.** Some rows hold a legacy opaque handle, some nothing, while its reserved future means a server-derived readable identifier. A tombstone and several successive lifetimes can share the handle. Selection still needs type, live scope, ambiguity behavior and locking; the handle does not remove those requirements.
5. **An explicit ID ceases to mean one lifetime.** Replaying a stale document against a tombstoned ID could silently update a newer lifetime. That is wrong for authored updates, removal targets, replication and expected-version checks. Without an explicit addressing distinction, the importer cannot infer which semantics the caller intended.
6. **Edge remapping is not enough.** Existing force-sweep membership uses literal envelope/endpoint IDs [tap_grid/grift/importer.py:2887](https://github.com/unified-systems-com/tap/blob/7100d9e20eabe57b7b487067dc980a7774cb4dc6/tap_grid/grift/importer.py#L2887). Existing enrichment can send edges with no node envelopes (see the prior plugin audit). Typed UUID payloads, hotlinks, cross-batch references and explicit deletes cannot all be repaired by remapping only in-batch edge endpoints.

Those are internal inconsistencies in B **as proposed**, not a request to invent aliases or restore hashing. My recommendation is A's explicit refs with existing explicit-ID addressing retained. Batch-local naming plus server-side facts lookup is a conventional separation; a UUID-shaped ref can still be an opaque local label, but must not quietly become persistent identity.

Strongest case against A: it requires schema and producer changes and forces decisions that B postpones. Accept that cost at the gate, because phase 3 already exists to change producers. Keep its first slice narrow: batch IDs remain explicit; nodes use refs with complete declared properties; endpoints may use refs or existing IDs; conflicting resolved writes are refused; unsupported nested-reference/removal/sweep combinations are rejected clearly until implemented. Include lock-and-recheck, whole-batch rollback and failed-attempt replay semantics before concurrent producers use it. Do not implement this list in phase 2.

## 7. Independent prior art: the useful comparisons and their limits

| System | Where it actually lands | What TAP should take from it |
|---|---|---|
| **Kubernetes** | Reusable object names are separate from lifetime UIDs. Garbage collection follows owner references and preserves dependents with remaining owners; it is not one database transaction over the whole closure. | Supports assigned lifetime identity, but challenges unconditional shared-child retirement. Do not call its GC the same atomic cascade as TAP. [Names](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/), [GC](https://kubernetes.io/docs/concepts/architecture/garbage-collection/). |
| **Datomic** | `isComponent` declares dependent parts; retractEntity recursively retracts components. Tempids and unique identity attributes solve transaction naming/upsert separately. | Strongest compact cascade analogue. Its identity uniqueness contract differs from TAP's deliberate nonuniqueness. [Schema](https://docs.datomic.com/schema/schema-reference.html), [retraction](https://docs.datomic.com/transactions/transaction-functions.html). |
| **Apache Atlas** | GUID entity identity coexists with unique qualifiedName lookup. Historical type-system documentation distinguishes composite relationships. | Supports separate row identity and readable lookup, not an argument that TAP must materialize another column now. Atlas's uniqueness is an important difference. [Type system](https://atlas.apache.org/0.8.3/TypeSystem.html). |
| **FHIR R5** | Conditional update has explicit zero/one/multiple-match outcomes; transactions resolve local resource references and fail atomically. Conditional interactions have trial-use status in R5. | Best protocol analogue for A: make local naming and search resolution explicit. It does not require a stored hash. [HTTP/transactions](https://hl7.org/fhir/R5/http.html#cond-update). |
| **JSON:API Atomic Operations** | Local IDs can link resources before server IDs exist; operations have defined atomic failure behavior. | Refs are established transport practice. The standard does not supply TAP's business-identity lookup. [Atomic extension](https://jsonapi.org/ext/atomic/). |
| **SCIM** | Server-assigned IDs differ from client externalId; bulkId references link operations. Bulk is not TAP-style all-or-nothing. | Good evidence for separating addressing roles; also shows why B's external handle is a separate semantic concept, not a free reinterpretation of `id`. [Core schema](https://www.rfc-editor.org/rfc/rfc7643.html#section-3.1), [protocol](https://www.rfc-editor.org/rfc/rfc7644.html). |
| **ServiceNow IRE** | Identification rules and source update authority are separate; duplicates have explicit remediation/configuration behavior. | Validates centralized fact-based identification. TAP need not import its policy machinery. [IRE concepts](https://www.servicenow.com/docs/r/servicenow-platform/configuration-management-database-cmdb/c_CompsandProcessIDandReconcil.html). |
| **DataHub** | URNs themselves identify resources and encode source/domain naming. | Useful readable-name examples, not an equivalent assigned-ID-plus-nonunique-secondary-key lifetime model. [Concepts](https://github.com/datahub-project/datahub/blob/master/docs/what-is-datahub/datahub-concepts.md). |
| **Data Vault / AutomateDV** | Both hash-based surrogate primary keys and hashdiff change detection exist. | Correct the rationale, retain hash withdrawal on simplicity grounds. This is not an exact endorsement of the old TAP digest. [Hashing](https://automate-dv.readthedocs.io/en/latest/best_practises/hashing/). |
| **Active Directory** | Assigned object identity, tombstones and richer recoverable deleted-object state coexist; reanimation remains documented. | Evidence of explicit lifecycle choices, not proof that TAP must restore or that AD abandoned all reanimation. [Tombstones](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-adts/89e942fa-e1f4-4c2e-ac3a-fd1b770a9799), [recovery](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/get-started/adac/active-directory-recycle-bin). |
| **TypeDB** | Its current reference calls `@cascade` a planned, unavailable feature. The described direction concerns deleting a relation when a role player disappears. | Remove it as proof of an already-established implementation of this precise subtree cascade. [Reference](https://typedb.com/docs/typeql-reference/annotations/cascade/). |
| **Django / relational transactions** | Explicit relation actions and atomic rollback are separate mechanisms; rollback does not undo arbitrary side effects. | Use the atomic boundary, but keep TAP's explicit tombstone traversal because ordinary FK deletion does not perform it. [Transactions](https://docs.djangoproject.com/en/5.2/topics/db/transactions/). |

The earlier survey additionally covers Neo4j lock/recheck, TigerGraph edge discriminators, Dataverse alternate-key upsert, Hibernate mutable natural IDs and Stripe request idempotency. They remain useful **gate/phase-3** comparisons, not reasons to grow phase 2.

## 8. What the audit missed, and the smallest sufficient done-test

The missed interactions are more important than another inventory sweep: explicit retirement already preceding phase 5; gate shape B colliding with authored-ID meaning; containment versus collection reachability; cap combined with cycles; per-edge provenance versus endpoint bulk updates; per-child authority claims versus current global capability enforcement; and docs describing three readers when only cascade exists.

For **phase 2**, require observed tests for: live-only 0/1/multiple lookup and absent values; real index migration; placeholder clearing/rejected external input; a contained chain with an external reference; ordinary and self-loop over-cap rollback; child refusal rollback; long-chain/cycle termination; and the exact provenance scope chosen. A repeated delete must have its intended version/event behavior asserted, not merely leave the row tombstoned. Keep the tombstoned-upsert batch fixture as premise verification. If GRIFT parity remains promised, its integration test is mandatory; otherwise mark it deferred.

For **the gate**, carry the earlier identity interactions forward: complete-key validation, same-batch aliases, concurrent absent matches, assigned lifetime mapping, explicit-ID OCC, deferred-hotlink behavior, batch replay/failure durability and supported removal/sweep combinations. For **phase 3**, add real ownership declarations and consumer identity/edge conformance. For **later passes**, keep preflight, operator repair, richer policies and performance work in their existing backlog homes.

**Decision:** proceed with the reduced architecture. Fix the cap defect before relying on it, choose truthful provenance and entry-point scope, and choose A at the next gate. Nothing found warrants restoring the withdrawn hash or making the full reconciliation framework a prerequisite for this pass.
