# Batch playground: review and corpus recommendations

2026-09-18. Review scope: the gate collision in **issue #602**, the proposed playground in **#603**, and importer/service behavior around those changes. Initial HEAD was `3d06470d`; Claude's fix committed as `bd2ff339` during review and subsequently opened as [PR #604](https://github.com/unified-systems-com/tap/pull/604). This is a handoff for Claude, not an implementation patch.

**Build a corpus of transactions and histories, not just graph snapshots.** The valuable unit is: starting grid → one or more submitted documents → committed grid, returned report, provenance, and unchanged surroundings. The existing #603 outline is good. Its strongest additions over the first cascade draft are a set-based oracle, input sequences, exact diagnostics and corrupted-result negative controls.

## Immediate code findings

These findings warrant regression scenarios before expanding the corpus. No shared database tests were run; validation below is deliberately explicit about that limitation.

Tracking: [#605 overall failure propagation](https://github.com/unified-systems-com/tap/issues/605), [#606 resolved-target collisions](https://github.com/unified-systems-com/tap/issues/606), [#607 rollback counters](https://github.com/unified-systems-com/tap/issues/607), [#608 clearing dimensions](https://github.com/unified-systems-com/tap/issues/608).

1. **Overall write failure is ignored by the importer.** `tap_grid/grift/importer.py:2613` consumes individual `WriteResult.success` values but ignores `BatchWriteResult.success/errors`. A precommit exception can roll back the inner write transaction while leaving only successful-prefix results. The importer can then run spine synchronization and close its outer batch. Two exact-AST probes in the project interpreter confirmed that both empty and successful-prefix results with overall failure proceeded to spine sync. The partial committed-spine consequence follows from the subsequent code and still needs a database regression. Inject failure at hotlink-drain/precommit, rather than assuming ordinary per-op exceptions use this branch.
2. **Resolved refs can collide with explicit IDs or removals.** Preflight compares provisional IDs; `_resolve_ref_identities` at2902 skips explicit-ID envelopes. The #602 key guard compares refs with other refs. Existing X plus `[ref resolving to X, explicit X]` therefore escapes the checks, as can a ref upsert plus removal of X. The independent reviewer confirmed the exact helper returns the substitution with no issue. Add post-resolution target-collision coverage, including both envelope orders.
3. **Rollback leaves inflated import counts.** The successful prefix increments node/edge counts; `_BatchFailed` at2801 clears upsert tracking but not those counters. Removal counters are cleared separately; global counts sum all batch summaries. Test valid-first/invalid-second and compare reported imports to committed rows, not attempted writes. Static finding.
4. **Explicit empty dimensions do not clear existing dimensions.** `_sync_spine_for_replaced_nodes` at3030 tests truthiness, so `{}` is ignored. The authoritative-envelope contract at `spec-grid-import-grift.md:195` says differences must be applied. Executing the exact function with an observation double confirmed no update for nonempty → empty. Test missing and explicit-empty separately.

Additional candidate, not yet reproduced end to end: multiple `write_batch` operations on one hotlinked node enqueue distinct intermediate instances, which are subsequently checked against final edges (`caller_context.py:158`, `services/_impl.py:990`). A transient layout A followed by final layout B and B's edges may be rejected against stale A. This belongs in service-batch integration coverage; GRIFT's duplicate-target prohibition should not be weakened to make it expressible there.

The probes are in `review/batch-playground-probes.py`. They execute selected unmodified importer code with memory doubles, touch no database and are evidence of control flow, not a substitute for integration tests.

Adapt the lesson to history/provenance: final payload alone does not prove intermediate records are correct. |

Adapt a tiny indicator–malware–organization–sighting graph first. STIX bundle membership is not an atomic transaction guarantee, and STIX IDs/versioning are not TAP IDs/tombstones. |

Do not use CouchDB bulk outcomes as TAP's expected answers. |

There is no off-the-shelf dataset here that certifies TAP unchanged. The strongest reusable assets are **small executable regression inputs and transaction schedules**, not millions of realistic records. Keep source links and reviewed revisions with adapted cases; author TAP expectations independently. Check upstream licensing before copying source fixtures verbatim.

The [HAPI FHIR conditional-create incident](https://github.com/hapifhir/hapi-fhir-jpaserver-starter/issues/459) supplies another useful historical reproducer: concurrent conditional creates of the same object produced duplicates. Treat it as a documented failure shape, not a claim about current HAPI behavior.

## Starter suite: cases that earn their place

These are scenario recommendations, not an executable schema. Each line should carry exact expected outcomes and map to an existing requirement or a named unresolved decision. Avoid a quota of five nearly identical cases per family when one cross-feature case is more discriminating.

| Family | Cases to include in the first pass |
|---|---|
| Ref syntax and scope | Envelope ID XOR ref; endpoint ID XOR ref; duplicate node ref; node/edge ref-name collision; missing ref; endpoint targeting an edge ref; same label independently reused in two batches; cross-batch ref rejected; blank/Unicode/whitespace labels according to the declared contract. |
| Lookup and identity | Zero/one/multiple live matches; same-key tombstone plus live row; tombstone-only return gets a fresh ID; KEYLESS always assigned; undeclared key refused; incomplete key behavior; composite keys sharing all but one component; same values on different types. |
| Collision after resolution | Two refs with equal key on empty grid (#602); same pair when existing; ref plus explicit existing ID; ref plus delete; ref plus purge; three aliases with one unrelated node to prove atomicity; ref resolving to a target also addressed in another batch. |
| Reference rewriting | Self-loop; two-node cycle; forward node ordering; diamond/shared target; existing and newly assigned endpoints; explicit unrelated endpoint untouched; payload text resembling a ref left untouched; all returned bindings agree with actual endpoint IDs. |
| Replace and provenance | Both name projections change together; dimensions change and clear; false/zero/empty lists/maps survive as values; omitted versus explicit null/empty; payload resets under replace rather than patch; all events/history attributable to the correct batch and actor; no provisional IDs recorded as if durable. |
| Atomic refusal | First/middle/last operation failure; schema failure versus model validation failure versus precommit failure; batch-level error with empty results and successful-prefix results; no residue in typed rows, spine, edges, history, events or batch infrastructure; counters equal committed effects. |
| Multi-batch document | Full-file preflight refusal produces no writes; late execution failure rolls back its own batch; earlier successful batch stays committed; unrelated later batch behavior follows the contract; later edge depends on failed earlier creation; forward cross-batch explicit endpoint; repeated refs across batches do not leak bindings. |
| Removals | Delete node and its incident edges; edge-only delete preserves nodes; missing and already-retired target policy combinations; expected-version checks on executable versus policy-skipped targets; explicit upsert/removal overlap and overlap revealed by ref resolution; DEBUG-only purge refusal; rollback after a late purge failure. |
| OCC | Matching/stale/future expected version; expectation on missing entity; conflict after earlier successful operation; OCC checked against resolved existing ID rather than provisional ID; no automatic retries; diagnostic actual version/path identifies the final target. |
| Dangling and edge identity | Missing source, target or both; tombstoned endpoint; strict refusal versus permissive skip with precise warnings; unrelated valid edge still lands in permissive mode; two distinct edge envelopes with equal endpoints/type, including endpoints that become equal only after ref resolution (#547). |
| Replay and force | Same batch ID replay skips unchanged; changed content under same ID does not silently reapply; same facts under a fresh batch resolve consistently; original caller dict remains byte/structure equivalent; retry a failed document; force denied outside DEBUG; force sweep cannot claim retirement beyond its contract. |
| Deferred consistency | Node and hotlink edge in one batch; replacement changes authoritative field and matching edges together; valid final graph with invalid intermediate graph; invalid final graph rolls back all; delete/purge interactions; repeated-node writes tested through write_batch, not illegal duplicate GRIFT envelopes. |
| Boundary integrations | Retired-type stripping only at its sanctioned seeding boundary; normal importer unknown-type behavior remains explicit; import-only actor versus removal-capable actor; actor/context restored after success/failure; one collector test proves errors cannot become a successful collection. |

Important identity distinction: explicit-ID writes currently bypass natural-key resolution. Do not invent a global uniqueness rule while writing tests. Same-key explicit-ID rows can be the setup for an ambiguity test. A ref resolving to the **same actual ID** as another operation is a different, already-prohibited collision.

Important replay distinction: same batch ID skipping, stable entity identity across fresh batches, and no-change history suppression are different promises. Do not demand zero version/history change on every fresh-batch re-observation while #322 remains unresolved.

## A few useful example datasets to author

1. **Two observations, one thing:** 2–4 fixture nodes; two source-shaped observations share the declared key. Variants: empty grid, existing live row, tombstone, second explicit ID, removal, stale version. This should be the first dataset family.
2. **Patient/encounter/observation shape, adapted from FHIR:** existing subject, new encounter and observations, shared references, a circular link variant and one failed conditional identity. Use neutral fixture types; no healthcare dependency or personal data.
3. **Host/application/interface shape, adapted from IRE:** composite `(source namespace, source ID)` keys, same display names with different keys, repeated observation from a second source and a genuinely ambiguous lookup. Preserve TAP's namespace semantics rather than adding source precedence.
4. **Account/contact/case shape, adapted from Salesforce:** dependency chain plus a disconnected successful component. Place the failure at each step and across two batches to distinguish transaction scope.
5. **Indicator/sighting graph, adapted from STIX:** two observations share indicator and organization nodes; relationships cross batch boundaries; one stale observation is removed. Keep it small enough to name every expected row/event.

Prefer 2–8 entities for the correctness fixtures. A separate moderate-size generated dataset can exercise chunk limits later. Reuse approved neutral fixture types or add dedicated test types for composite keys/hotlinks; do not make core tests accidentally depend on a consumer plugin's seeds.

## Checker and oracle requirements worth deciding now

**Observe three separate truths:** persisted state, API report, and audit/provenance. Every success/refusal must agree across all three. Compare complete relevant field values, actual tombstone timestamps, versions, edge endpoints/properties, batch ownership and history/event deltas. Preserve and compare unrelated sentinel rows. A Boolean tombstone flag alone misses a rewritten deletion timestamp.

**Treat generated IDs symbolically.** Authored expectations should express equality/distinctness and UUID requirements, not predict a minted ID. On a failed batch, returned provisional mappings must never be treated as proof of committed rows. Explicitly test caller input immutability and that mappings do not leak across requests.

**Keep the oracle structurally independent.** Compute candidate identity matches and resolved target equivalence classes from the declared starting state; validate conflicts; derive the final graph and record deltas; apply the declared transaction boundary. Don't copy importer loops, call production identity helpers or use importer return values to calculate expected output. Schema-only validation is not a full dry-run oracle.

**Add metamorphic checks where the contract permits:** consistently rename local refs; permute independent node/edge declarations; add a disconnected sentinel; reuse the same ref label in a different batch. Expected logical results should be invariant modulo generated IDs. Do not assert invariance under arbitrary batch reordering, splitting one atomic batch, or replacing explicit-ID addressing with refs; those can legitimately change behavior.

**Negative controls should corrupt different evidence layers:** wrong binding; extra row; changed survivor; missing/duplicate event; wrong batch attribution; inflated committed counter; overall failure ignored; lost empty value; wrong error path; root or child version bumped twice. Each corruption must make the checker fail. Pending outcomes must recognize the exact defect in-body; setup errors, worker crashes and deadlocks remain hard failures.

## Timing: a few schedules now, broader exploration later

Start with same natural key in two writers on an empty grid; opposite key acquisition orders A→B / B→A; same explicit batch ID replay race; ref writer versus explicit-ID writer; and identity lookup racing with deletion of the matched row. Some outcomes may require a contract decision: record that decision rather than accepting whichever result occurs once.

Use actual per-writer synchronization and identified backend/lock relationships. Capture worker failures; release/join in finally blocks; state which serial outcomes are acceptable. A barrier only at thread start does not prove the vulnerable overlap. A typed conflict with no committed partial work may be a valid outcome; don't require both writers to succeed unless the contract promises that.

## Defer without weakening the first pass

- Full STIX reports, broad synthetic FHIR populations, performance/soak testing and many-worker chaos runs.
- New property-testing dependencies, generalized shrinkers, cross-database differential execution and a generic playground framework.
- Collector-wide exactly-once delivery guarantees, source reconciliation priority, and global natural-key uniqueness. These are separate contracts.
- Copying every ordinary validation test into JSON. Prefer targeted compositions and retained minimal counterexamples.

The immediate completion criterion should be that the suite would catch #602 **and the adjacent post-resolution/rollback/reporting defects above**, not just that it contains fifty files. Existing known issues #351 (hotlink replacement), #361 (sweep/reference interaction), #547 (edge collapse), and #322 (re-observation history) should have explicitly classified regression or pending cases where they fall within scope.
